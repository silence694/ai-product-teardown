# 拆解内容手册

图解决「可信度」，文解决「洞察力」。这份文档规定拆解正文怎么写才不像通稿。

---

## 一、六维观察框架

拆一款产品，从这六个维度里挑 2-3 个展开，其余一句话带过。**不要六个都写**——均匀用力等于没有重点。

| 维度 | 观察什么 | 好的问题 |
|---|---|---|
| **任务流** | 用户从进入到完成目标的路径 | 完成核心任务要点几次？哪一步最重？能不能跳过？ |
| **能力边界** | 它明确做不到什么 | 官方文档里的「限制」「不支持」「注意事项」写了什么？ |
| **抽象层级** | 把复杂事情包装成什么概念 | 它把「模型调用链」抽象成「工作流」还是「Agent」？这个抽象漏掉了什么？ |
| **默认值** | 产品替用户做哪些决定 | 新建时预填了什么？默认配置暴露了产品对用户水平的假设 |
| **失败处理** | 出错时给什么反馈 | 任务失败后能重试吗？能看到中间过程吗？错误信息是给开发看的还是给用户看的？ |
| **商业化切口** | 从哪一步开始收费 | 免费额度卡在哪个环节？这个位置暴露了产品的价值锚点 |

**默认值和失败处理是最容易被忽略、也最能体现产品功力的两维。** 竞品分析扎堆写「功能对比表」，写不出这两维；面试里能聊这两维的人立刻区分开。

## 二、功能描述的三层颗粒度

每个核心功能必须写满三层，缺一层就是没写透。

### 第一层：是什么（客观描述）

一句话说清这个功能做什么，不含评价。

> 「资产市场是 AgentArts 的公共组件库，把插件、知识库、提示词模板打包成可复用资产。」

### 第二层：怎么用（控件级还原）

这是核心。让读者不看图也能脑补出界面。

> 「入口在左侧导航第三项。列表按调用量排序，每张卡片右上角标三个状态：是否付费、是否需要鉴权、工具数量。点进详情页，顶部是 README 渲染结果，下方分「工具列表 / 调用示例 / 版本记录」三个页签——说明它把插件当成有生命周期的软件包在管，而不是一段配置。」

判断标准：**能不能数出页面上的元素个数。** 「三个状态」「四个页签」「两列布局」——有具体数字就说明真的看清了。

### 第三层：为什么这么设计（推断 + 证据）

从界面反推产品决策，必须给证据，不能空口猜。

> 「把『是否需要鉴权』做成卡片上的显性标签，说明插件生态里最大的摩擦力是接入成本而非功能丰富度——用户选插件时先问『我要不要申请 key』，而不是『它能不能干这事』。」

**禁止**：不给证据的动机推断（「这说明团队很重视用户体验」）。要么给出界面证据，要么写成待验证的假设（「可能的原因是……」）。

## 三、caption 写法

caption 是报告里信息密度最高的文字。一张图配 20-40 字，必须包含三要素：

```
【哪个页面/场景】+【能看见哪几个具体控件】+【这说明了什么】
```

### 对照表

| ❌ 差 | ✅ 好 |
|---|---|
| 产品界面截图 | 创建单智能体 · 基础信息：左栏四个必填项（名称/描述/图标/分类），右栏是智能体对客形态的实时预览，改名称右侧同步更新 |
| 功能很强大 | 插件广场：三个页签（全部/官方/第三方）+ 卡片标注付费状态、鉴权要求、工具数量、数据来源域名 |
| 官方演示 | 评估任务列表：任务名 / 评测集 / 评估对象 / 对象类型四列并列，支持批量勾选后一键重跑 |
| 智能体商店 | 智能体商店首页：分类导航 12 项 + 卡片展示作者、调用次数、更新时间，无「官方认证」标签 |
| 示意图 | 工作流编排画布：节点从左侧组件库拖入，连线处显示变量映射，右下角有试运行按钮 |

### 三个禁忌

1. **不许写「示意图」「产品截图」「官方图片」** —— 这等于没写
2. **不许只描述画面不写控件** —— 「界面上有三个卡片」这种要具体到卡片上有什么
3. **不许超过 60 字** —— 超了读者不看

### 资讯图的特殊标注

D 级来源的图，caption 末尾必须加「（资讯配图）」。这不是免责，是让读者知道该图的证据强度低于界面截图。

## 四、Takeaway 写法

三条方法论，每条独立成立，能直接搬进面试回答。

### 结构

```
【一句话主张】+【支撑证据】+【可迁移的条件】
```

> **评估能力是 Agent 平台的分水岭。**
> AgentArts 把「评估任务」做成一级导航，和「智能体」「工作流」平级，配置项包括评测集、评估对象、对象类型；而早期平台只提供对话调试。
> 当一个品类的用户开始问「效果稳定吗」而不是「能做什么」，评估、回归、监控就会从附加功能变成基础设施——这条规律在推荐系统、搜索、模型训练上都成立过。

### 判据：能被反驳

写完自检：如果有个同行说完全相反的版本，会不会引起争论？

- 「好的设计提升体验」→ 没人反对 → 废话
- 「Agent 平台的竞争点已从『能不能建』转到『建完怎么评估』」→ 有人会说「现在还早，用户还在拉新阶段」→ 有价值

### 三条要互相不重叠

常见的错误是三条 takeaway 都在说「这个产品做得不错」。正确姿势是分别覆盖：

1. 一条关于**行业阶段**（这个赛道走到哪了）
2. 一条关于**设计方法**（可复用的具体做法）
3. 一条关于**风险或反面**（这个做法在什么条件下会失效）

第三条最容易被跳过，但它是把「产品夸夸群」变成「产品分析」的关键。

## 五、注水表达黑名单

出现以下表达，立刻删掉换成具体描述。这些词在报告里等于噪声。

| 黑名单 | 为什么不行 | 替换成 |
|---|---|---|
| 界面简洁、体验流畅 | 无信息量 | 具体控件数量与布局方式 |
| 功能强大、生态丰富 | 无法证伪 | 列出功能模块数量 + 举 2 个具体能力 |
| 大幅提升效率 | 没有基线 | 「从 5 步减到 3 步」/「省掉一次人工审核」 |
| 赋能、闭环、抓手、颗粒度 | 行话遮羞 | 直接说做了什么动作 |
| 深度融合 AI | 空 | 指出 AI 具体嵌在哪一步、输入输出是什么 |
| 行业领先、首个 | 需查证 | 给出时间点或来源；查不到就删 |
| 预计将达 XX 亿 | 二手预测 | 用官方披露的真实数据 |
| 极大地、非常、十分 | 程度副词 | 删掉，或用倍数/百分比 |

## 六、数字使用原则

1. **每个数字都要能指到 `sources` 里的某一条**，用 `cite` 字段标注
2. **不写没出处的百分比**。「提升 30%」必须说明是谁测的、怎么测的
3. **区分三种数字**：官方披露（可引用）、第三方测算（标注测算方）、自己估的（写「据界面推断」，且不给精确数字）
4. **指标卡放 4 个就够**。塞 8 个指标卡的结果是读者一个都记不住

## 七、对比表怎么写

Takeaways 那一节必配一张对比表。三种可用的切法：

### 按能力切

| 能力 | 本产品 | 竞品 A | 竞品 B |
|---|---|---|---|
| 可视化编排 | 支持，节点级调试 | 支持，无单节点调试 | 不支持 |
| 效果评估 | 一级导航，支持评测集 | 二级菜单，仅对话回放 | 无 |

**注意**：不能只列「支持/不支持」，要带一句差异说明。只写「支持」的对比表是功能清单，不是分析。

### 按用户角色切

按「开发者 / 业务人员 / 管理员」分别看谁能完成什么，能暴露产品真正的目标人群。

### 按阶段切

把同类产品按时间排开（2023 / 2024 / 2025），看功能重心的迁移。这种表最能支撑「行业阶段」类结论。

## 八、篇幅控制

**正文 1500-2500 字。** 超过 3000 字的拆解基本没人读完。

分配建议：

| 部分 | 字数 | 说明 |
|---|---|---|
| Overview | 250-350 | 为什么是今天、为什么是它 |
| Feature 01 | 350-450 | 主功能，写得最细 |
| Feature 02 | 300-400 | 次功能 |
| Feature 03 | 250-350 | 补位功能，可以简洁 |
| Architecture | 300-400 | 机制解释 + 四步流程 |
| Takeaways | 250-300 | 三条方法论 + 对比表 |

写超了怎么砍：**先砍第三个功能，再砍 Overview 的背景铺垫，最后砍架构的技术细节。** 不要砍 caption——那是密度最高的部分。
